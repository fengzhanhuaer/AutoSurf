## 一、需求定义

### 1.1 背景与问题

当前任务、执行记录、候选站点发现、备份恢复和设置界面仍围绕 `CredentialRecord`、CookieCloud 与 Web 凭据同步。虽然浏览器任务已经能够读取常驻 Chrome 环境，队列仍保存凭据快照，PT 与 NodeSeek 的创建接口仍要求同步凭据。

### 1.2 目标

让常驻 Chrome Profile 成为浏览器自动化唯一登录态来源，移除 CookieCloud、Web 凭据及任务凭据快照的运行依赖和管理入口。

### 1.3 范围、非范围与约束

- 范围内：数据库 schema、启动装配、任务与队列服务、PT/普通站点候选和创建 API、管理前端、备份恢复、远程 Chrome 声音、测试与文档。
- 范围外：迁移旧凭据或旧任务数据、线上部署、改变 Chrome Profile 持久化目录、改变登录和局域网访问控制、删除在线升级能力。
- 约束：PT 与普通浏览器任务运行时只读取 Chrome 当前 Cookie/Web Storage；纯 HTTP 任务不得隐式使用同步凭据；不使用 HomePc 测试。

### 1.4 需求与验收标准

## 二、总体架构

### 2.1 当前现状

`main.create_app` 创建 `CredentialService`、`CookieCloudStore`、`WebCredentialStore`；`QueueService` 将凭据写入执行快照；候选 API 查询凭据表；浏览器控制启动时还执行一次凭据注入。

### 2.2 目标架构

数据库仅保存自动化、执行记录和系统设置。队列只快照任务配置。浏览器任务打开站点后从常驻 Chrome Profile 读取 Cookie、LocalStorage 与 SessionStorage。PT 与普通候选由静态站点目录提供，任务只绑定站点 URL 和动作配置。

### 2.3 关键模块与职责

| 模块 | 当前职责 | 目标职责 | 输入 | 输出 | 依赖 |
|---|---|---|---|---|---|
| 应用服务 | 凭据 CRUD、快照、调度 | 无凭据的任务/队列/执行 | 任务配置 | 执行结果 | 数据库、处理器 |
| PT/周期 API | 从凭据发现并创建任务 | 从目录发现并创建任务 | 站点键或 URL | 任务视图 | 站点目录 |
| 浏览器运行时 | 首次注入并读取环境 | 只读取并持久化 Chrome 环境 | 页面与 Profile | 运行上下文 | Chrome |
